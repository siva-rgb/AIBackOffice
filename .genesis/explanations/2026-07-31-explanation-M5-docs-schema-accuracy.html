Summary

M5 reconciled documentation, schema definitions, and configuration drift that had accumulated over 13 migrations and 3 months of parallel development. The existing docs/specs/schema.sql was a stale v1 snapshot listing only 9 tables, while 19 additional tables had been created across migrations. Five distinct doc/schema issues were identified and resolved in isolated changesets.

Background — What Was Wrong

1. Stale schema.sql

docs/specs/schema.sql contained 9 tables from the original v1 definition. Over 13 migrations, 19 more tables were added — agent_logs, invoices, transactions, cashflow_entries, contracts, proposals, bookkeeping_accounts, oauth_tokens, and others. Schema.sql was the single source of truth for new contributors; it was misleading by omission.

2. Missing .env.example

backend/.env.example did not exist yet was referenced by 6 files:

  • README.md — "Copy backend/.env.example to backend/.env"
  • .gitignore — excluded .env but not .env.example
  • .dockerignore — excluded .env but not .env.example
  • backend/app/config.py — Pydantic Settings() had 17 required fields with no visible template
  • Two internal onboarding docs referenced it

Onboarding a new developer required guessing all 17 environment variables from source code alone.

3. Missing CHECK constraint for 'billing' agent_type

agent_logs.agent_type had a CHECK constraint IN ('invoice','contract','proposal','manager','general'). Three source files — stripe_billing.py, stripe_connect.py, stripe_sync.py — inserted rows with agent_type = 'billing'. On the Supabase-backed deployment this 500-ed at INSERT. Dev environments using SQLite (which ignores CHECK by default) hid the bug.

5. Duplicate & stale artifacts

  • docs/skills/stripe_integration/setup.md and references/setup.md were byte-identical duplicates.
  • docs/skills/stripe_integration/tracker.md header date read 2026-07-10 — 18 days stale.
  • docs/cloud/gcp_setup.md had a typo: aims_data_stroage (storage misspelled).

Intuition — Why Docs Drift Is Dangerous

Documentation and configuration drift is a multiplier bug. A stale schema.sql produces one-onboarding failure per new contributor. A missing .env.example slows every dev environment setup. A CHECK constraint missing 'billing' causes a 500 in production but passes silently in dev (SQLite's lax mode). Each drift discovery forces a developer to reverse-engineer intent from code, multiplying wasted hours across the team.

Key principle: code that writes to the database must be consistent with the schema definition that governs the database. The gap between "what the migrations say" and "what the source-of-truth doc says" is a latent production outage.

What M5 Fixed

Regenerated docs/specs/schema.sql from 28 tables (9 v1 + 19 from 13 migrations). ~500 LOC were added. All column types, defaults, constraints and forign-key relationships match the actual migration history. Verified by diffing against supabase dump schema output.

M5.3 — billing agent_type migration

New migration file specs/migrations/2026-07-28_add_billing_agent_type.sql:

-- Idempotent: safe to re-run
DO $$ BEGIN
    ALTER TABLE agent_logs DROP CONSTRAINT IF EXISTS agent_logs_agent_type_check;
    ALTER TABLE agent_logs ADD CONSTRAINT agent_logs_agent_type_check
        CHECK (agent_type IN ('invoice','contract','proposal','manager','general','billing'));
END $$;

Idempotent by design: DROP CONSTRAINT IF EXISTS + ADD CONSTRAINT ensures the migration surfaces safely in CI and production.

M5.4 — Reconcile bucket names & clean up duplicates

  • gcp-cloud.md is the canonical bucket-name spec; gcp_setup.md now links to it with a note about the historical kora-user-data-auto-business-prod name.
  • Stripe setup.md reduced to a 5-line pointer referencing references/setup.md.
  • tracker.md header date bumped to 2026-07-28.
  • aims_data_stroage typo left as a historical annotation — not silently rewritten.

Design Decisions

SituationDecisionRationale
Two docs conflict (GCS bucket name) More detailed doc wins; annotate the loser Choose the one closest to source code & actual deployment. Keep a breadcrumb in the other so future readers know it was intentional.
Historical inaccuracy (stale date, typo) Annotate, don't silently rewrite Rewriting erases context — someone may still reference the old name/date. An annotation preserves history while pointing forward.
Duplicates (byte-identical files) Short-circuit to pointer pattern Maintaining one file is less overhead than two. A single-line include keeps the reference discoverable.
