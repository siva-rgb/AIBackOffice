## Quiz-me Q+A (L4 protocol)

**Q1 · Design decision:** Why was the mock-mode escape hatch (`_fernet = None` when `KORA_DATA_BACKEND == "mock"`) removed, even though the context-graph invariant `inv_token_encryption_startup` only required fail-closed in production mode?
**A:** The mock backend is for **unit tests** (it never serves real traffic). The escape hatch existed to make the dev experience slightly nicer (no need to set a key to run with mock data). The cost of that convenience was a hidden failure mode: any developer who switched from mock to supabase mode **without** setting `TOKEN_ENCRYPTION_KEY` would silently produce a working-but-destructive build (encrypts with key A today, decrypts with key B tomorrow). Strict reading of the invariant ("never silently destroy encrypted tokens") and strict reading of M3.2 ("process exits with a clear error") both point to the same place: fail-closed at module import, period. Tests still get a working fixture because `conftest.py` pins a fixed Fernet key — so the dev experience is preserved **for tests** without sacrificing the production contract.

**Q2 · Edge case:** What happens if `TOKEN_ENCRYPTION_KEY` is set but contains only whitespace (e.g. an accidental trailing newline from a copy-paste)?
**A:** `_read_key()` calls `.strip()` before checking for emptiness, so a whitespace-only key triggers the "is not set" branch — `StartupError` with the same descriptive message. This was specifically covered by `test_load_key_raises_when_whitespace` (passes). The rationale: whitespace is never a valid Fernet key, and silently coercing it to "" would give the operator less diagnostic information than failing with the same error as a truly missing key.

**Q3 · Change impact:** The `conftest.py` change pins a specific Fernet key as `TOKEN_ENCRYPTION_KEY` for the test suite. Does this affect any test that does NOT go through `conftest.py` (e.g. someone running a test file directly with `pytest path/to/test_x.py`)?
**A:** No. `pytest` discovers and runs `conftest.py` before any test module — that's the standard pytest contract. Any `pytest` invocation from the `backend/` directory (or any subdirectory) will load `conftest.py` first, which sets `TOKEN_ENCRYPTION_KEY` before any `app.*` import. The one edge case is `python -m unittest` (bypasses pytest's conftest mechanism) — but the project uses pytest exclusively per the M2 baseline (see `pytest.ini`), so this is not a real risk. If a future contributor switches to `unittest`, they would need to set the env var themselves; this is documented as a non-goal for M3.
