1. Background

Kora stores personal data across 28 tables for each user. GDPR Articles 15 (right of access), 17 (right to erasure), and 7 (consent) require three things: export all data, delete all data, and prove consent was given.

Before M9, routers/account.py had endpoints but they were dangerous: skipping 8 of 28 tables in the hard-coded list, silent try/except everywhere hiding failures, and an audit table referenced that didn't even exist in the migration history.

2. Intuition — The Fragile Before

BEFORE (hard-coded, 8 tables missed)
DELETE_TABLES = [
  "transactions", "invoices", "contracts",
  "clients", "engagements", ...
]  # only 20 of 28 tables
for table in DELETE_TABLES:
    try:
        db.table(table).delete().eq("user_id", uid).execute()

M9.2: Delete endpoint — DELETE /api/account/delete


The 7-step pipeline:


Step 1: Google OAuth revoke (best-effort)
Step 2: Stripe subscription cancel
Step 3: GCS file deletion (storage.delete_user_data)
Step 4: DB wipe: all 28 USER_DATA_TABLES + users row
    → per-table row counts via repo() + raw_table()
Step 5: auth.admin.delete_user(user_id)  (best-effort)
Step 6: record_deletion() — audit log, no PII
     "id: random UUID, reason, tables_cleared, files_deleted"
Step 7: Return structured side-effect report

Response:
{ "deleted": true, "user_request_id": "",
  "files_removed": 5,
  "tables_cleared": { "transactions": 142, "invoices": 3, ... },
  "side_effects": { "auth_delete": "done", ... } }




M9.3: Consent — POST /api/account/consent


Two consent capture paths:


# Path 1: explicit POST /api/account/consent
# body: { "version": "2026-06-01" }  (defaults to CURRENT_CONSENT_VERSION)
store.update_user(user.id, {
  consent_version: body.version,
  consent_given_at: now,
})

# Path 2: autoconf-reported onboarding (idempotent)
# routers/users.py::update_me
if patch.onboarding_completed and not user.onboarding_completed \
   and not existing.consent_version:
    store.update_user(user.id, {
        consent_version: "2026-06-01",
        consent_given_at: now,
    })
# Never overwrites existing consent — idempotent guard



4. Key Design Decisions




Table registry over schema derivation
A hand-maintained Python tuple in user_data.py instead of information_schema querying. Why: mock backend has no information_schema; manual allow-list excludes non-PII tables (deletion_log, config); FK child-before-parent ordering needs manual curation.


Structured side-effect reporting
Export returns per-table record count alongside full rows. Delete returns "{table: }" per table. No silent failures — the audit row records what was cleared.


No-PII audit trail
deletion_log has no user_id column, random UUID. Even a GDPR audit row cannot re-identify a user from the admin log itself. GDPR Art. 5(1)(c).


No consent overwrite
Onboarding completion captures consent exactly once. A second toggle never overwrites existing consent_version. Pre-M9 users need re-consent UX (out of M9 scope).

    6. Quiz — 5 Questions
    

    

    Q1. Why is a hand-maintained Python tuple preferable over information_schema for the table list?
      

    • It has better runtime performance than information_schema queries
      • 

    • The mock backend has no information_schema to query — a Python constant is the lowest common denominator for both backends
      • 

    • information_schema is deprecated in PostgreSQL 15+
      • 

    • White Python can be more expressive than SQL introspection
      • 

    

    Performance is not the driving factor — correctness parity is.
    B is correct. The mock backend has no database at all — information_schema would fail. The Python tuple works identically in both backends.
    information_schema is not deprecated — it's fine in PostgreSQL 15+. The issue is mock mode.
    The tuple doesn't need to be more expressive — it just needs to be shared across mock and supabase backends.
    


    Q2. What if the Supabase admin.delete_user call fails (network error / admin API down)?
    

      

    • The entire deletion is rolled back
      • 

    • The business PII is still deleted; the auth identity lingers — the endpoint returns "side_effects.auth_delete": "skipped: " so the operator sees the failure
      • 

    • The user's auth identity is retained but the row is marked as "pending-delete"
      • 

    • The deletion halts with a 500 error
      • 

    

    The user's data is already wiped. rollback doesn't make sense here.
    B is correct. If step 4 DB wipe succeeds but step 5 admin delete fails, the business PII is gone, the (non-Supabase) auth identity is gone, and the return carries a structured notice. The operator can re-issue admin delete later.
    No pending-delete state — the admin delete simply fails separately.
    It doesn't 500 — the DB wipe happened successfully. The admin delete failing is a separate, logged side effect.
    


    Q3. After M9: post-delete, what does a GET /api/account/export return for the deleted user ID?
    

      

    • A 404 NOT FOUND — the profile is gone
      • 

    • A 401 or 403 — because the auth identity is removed, the request has no valid token
      • 

    • An empty wrapper {format_version: 1, profile: null, tables: {}}
      • 

    • A 200 with some residual metadata about the deletion
      • 

    

    By post-deletion, if the caller's token works, new queries return 0 rows. But the auth was deleted — so authentication should fail first.
    B is correct. The deletion process removes the auth identity in step 5. A post-deletion request with the same token should fail auth — the auth identity no longer exists. Even if auth were bypassed, the export returns zero for all tables ("test_post_delete_export_returns_no_residual_pii").
    The JSON shape is real but the auth was deleted first.
    No metadata about the deletion remains in any data-table read.
    


    Q4. For a user already onboarded before M9, how do they obtain a consent_version?
    

      

    • It is auto-captured at first login after M9 deploys
      • 

    • The backend explicitly records it during any POST to any endpoint
      • 

    • Only POST /api/account/accept explicitly — pre-migration users are a special re-consent UX path
      • 

    • Their consent_version defaults to current during any API call
      • 

    

    Auto-captures have potential GDPR violation — consent is explicit not automatic.
    No automatic capture on random endpoints.
    C is correct. The onboarding-completion hook fires only when onboarding_completed flips false \rightarrow true — already-onboarded users never see this code. The only path is POST /api/account/consent (which Kora can prompt on-screen as a "terms update" re-consent UX).
    Not auto-recorded — it must be user-called explicitly.
    


    Q5. Why does deletion_log have no user_id FK despite many tables having it?
    

      

    • For maximum query performance on log listings
      • 

    • BELD_Model SQL constraint rules require it
      • 

    • GDPR Art. 5(1)(c) — the audit trail itself must not become a re-identification vector
      • 

    • Supabase RLS doesn't support logging
      • 

    

    Not about query performance.
    No SQL constraint rule forbids FKs.
    C is correct. The audit rows carry per-table counts and a random user_request_id but NOT a database-level user_id. This prevents the audit log from being a correlation vector that re-identifies users. Support can correlate via the request_id only.

    Supabase SQL interface supports FK constraints fine — it's a design choice.
