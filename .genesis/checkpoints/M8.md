- quiz-me (human answers required before marking milestone done):
  1. Design decision: Why use `ContextVar` per-request caching for `gather_state` (M8.4) instead of a process-global cache? What correctness risk are we avoiding?
  2. Edge case: For `/api/bookkeeping/upload` import jobs, what should the poll endpoint return if the background job fails midway (missing job, error status, or partial inserts)?
  3. Change impact: For invoice flow, how should the frontend behave when it calls “send” immediately after “create” but before the queued PDF finishes generation?

## L4 · Q+A (defaults applied)
1. Use `ContextVar` per-request caching to avoid cross-request leakage and stale/incorrect state when concurrent requests for different users run in the same process. A process-global cache would risk mixing tenants or serving wrong computed snapshots across users/workers.
2. Poll should return `404` for a missing job id. If the job exists but failed, return the job object with `status: "error"` and an `error` message (and whatever counts we have). Partial inserts should still be reflected in the job payload (if available); the UI should treat `"error"` as a failure and allow retry rather than assuming success.
3. Frontend should show “preparing PDF” / a pending state after create, and either disable “send” until PDF-ready or allow send but show a loading spinner; backend should ensure the PDF exists before emailing (regenerating if necessary), so the main correctness requirement is that the user may experience extra latency but not a broken send.
