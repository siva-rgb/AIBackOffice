## Implementation Review

### Core modules

#### `backend/app/utils/request_context.py` (89 LOC)

**Purpose:** ContextVar-based request/user id storage.

**Key details:**
- Two `ContextVar`s: `_request_id_var`, `_user_id_var` (both default to `None`)
- `begin_request_context(*, inbound_request_id, user_id)` — opens scope, re-uses inbound if uuid4-shaped, else mints new
- `end_request_context()` — closes scope (idempotent)
- `_is_uuid_hex()` — validates inbound `X-Request-ID` header (rejects non-hex, prevents attacker pinning to guessable id)
- `snapshot()` — returns both values at once (used by Sentry tags)

**Review:**
- ✅ Pure (no I/O, no state)
- ✅ Defensive (rejects garbage inbound header)
- ✅ Idempotent (`end_request_context` safe to call twice)
- ✅ Mirrors existing `request_cache.py` pattern (familiar to team)

**Risk:** Low. Straightforward ContextVar management.

---

#### `backend/app/utils/pii_scrubber.py` (166 LOC)

**Purpose:** Pure function `scrub(value)` — walk any Python value and redact secret-shaped substrings.

**Design rules enforced:**
1. **Pure** — no globals, no I/O, no time checks
2. **Conservative** — when in doubt, redact (false positives recoverable; false negatives leak secrets)
3. **Recursive** — handles dicts/lists/tuples/strings
4. **Allowlist + Deny-list** — `_SAFE_KEYS` (pass through) + `_SECRET_KEYS` (always redact value)
5. **Pattern catalog** — 8 regex patterns, pinned by unit tests

**Catalog:**

| Pattern | Coverage |
|---|---|
| `Bearer\|Basic` + base64 | OAuth2 / HTTP Basic |
| `eyJ` + two dots | JWT tokens |
| `sk_live_\|rk_live_` | Stripe live keys |
| `sk_test_\|rk_test_` | Stripe test keys |
| `api[_-]?key\|secret\|token` + 16+ chars | Generic API blobs |
| `\d{13,19}` + word boundaries | Credit card numbers |
| RFC-5322 email | Email addresses |
| `\d{3}-\d{2}-\d{4}` | US SSN |
| `\d{9}` + word boundaries | US bank routing |

**Review:**
- ✅ Pattern order independent (each regex applied once, all matches replaced)
- ✅ Case-insensitive key matching (handles `Authorization` / `authorization` / `AUTHORIZATION`)
- ✅ Recursive descent safe (dict/list/tuple/string/number/bool all handled)
- ✅ Catalog pinned — can't grow silently (test will fail)
- ✅ False-positive: `\d{9}` may match 9-digit sequences in benign contexts, but over-redaction is safer than leaking secrets

**Risk:** Low. Conservative redaction strategy is the right call.

#### `backend/app/middleware/access_log.py` (189 LOC)

**Purpose:** Pure ASGI middleware — emit one structured JSON line per HTTP request.

**Architecture:**
- Implements ASGI3 interface directly (not `BaseHTTPMiddleware`)
- Lifecycle:
  1. Extract inbound `X-Request-ID` header (if present and uuid-shaped)
  2. Call `begin_request_context(inbound_request_id=...)` to set up ContextVar
  3. Wrap `send()` to inject `X-Request-ID` into response headers
  4. After request completes (in `finally`), emit one JSON line via `kora.access` logger
  5. Call `end_request_context()` to clean up

**JSON line fields:**
```json
{
  "ts": "2026-07-29T10:00:00.000Z",
  "request_id": "abc123...",
  "method": "GET",
  "path": "/api/agents/log",
  "route_template": "/api/agents/log",
  "query": {},
  "status": 200,
  "latency_ms": 42,
  "user_id": "uuid..." | null,
  "client_ip": "1.2.3.4",
  "user_agent": "kora-frontend/...",
  "headers": {}
}
```

**Safety guarantees:**
- ✅ **Never raise** — catches its own exceptions, falls back to `print()`
- ✅ **PII scrubbing** — query + headers walked through `scrub()` before emit
- ✅ **Pure ASGI** — ContextVar writes visible to downstream services (decision 1 in M11.md iter 1)
- ✅ **Request ID echo** — response always gets `X-Request-ID`, so clients can quote it in support tickets
- ✅ **5xx handling** — even unhandled exceptions emit an access line with status 500 (important for post-mortem)

**Middleware ordering:**
- Placed outermost (first to run) in `main.py` line 105
- Captures final status code + total latency ✓

**Review:**
- ✅ Choice of pure ASGI over `BaseHTTPMiddleware` correct — ContextVar loss bug documented
- ✅ `_safe_emit()` defensive (two layers of exception handling)
- ✅ Client IP extraction handles `X-Forwarded-For` for reverse-proxy deployments
- ✅ `_headers_dict()` pre-drops sensitive headers at the source (before scrubber even runs)

**Risk:** Low. ASGI interface is standard; exception handling is defensive.

## Architecture & design decisions

### Decision 1: Pure ASGI middleware (not `BaseHTTPMiddleware`)

**Rationale:** `BaseHTTPMiddleware.dispatch()` runs `await call_next(...)` on a spawned anyio task, which **loses `ContextVar` writes** from the outer task (documented Python behaviour, not a Starlette bug). The end-to-end test failed under `BaseHTTPMiddleware` and went green immediately under pure ASGI.

**Trade-off:**
- Pure ASGI requires manual task scoping and send wrapping — slightly lower-level
- But guarantees ContextVar visibility to downstream service code ✓

**Precedent:** Starlette team recommends pure ASGI for observability middleware (same reason).

---

### Decision 2: Dual-write user_id to ContextVar + `request.state`

**Rationale:** Same BaseHTTPMiddleware task boundary issue. `get_current_user` (auth dependency) runs inside the spawned task, so its ContextVar writes don't propagate back to the access-log middleware on the outer task.

**Solution:**
- `_stamp()` helper writes user_id to both slots
- ContextVar is the fast-path for services
- `request.state` survives the task boundary for middleware

**Trade-off:** Dual-write adds 2 LOC; mirrors existing pattern in `request_cache.py`.

---

### Decision 3: `request_id` rides inside `output` JSONB envelope (no schema change)

**Rationale:** Avoids DB migration + RLS touch. Follows existing `_cost_usd` / `_provider_name` pattern (proven on M4–M8).

**Trade-off:**
- Pro: zero downtime, no migration, backward-compatible
- Con: JSONB lookup doesn't use an index (follow-up candidate `FU-M11-request-id-index` if needed)

**Precedent:** Successful use on cost tracking (M4) + provider name (M8).

---

### Decision 4: Zero new dependencies

**Rationale:** M11 implements structured access logs + correlation layer that is **OTel-compatible** (any OTel collector can ingest the JSON lines without code changes). Real OTel SDK + OTLP exporter deferred to `FU-M11-otel-sdk`.

**Trade-off:**
- Pro: no new dependencies, simpler deployment
- Con: no automatic baggage propagation to external services (out-of-band manual header passing remains option)

**Precedent:** Aligns with zero-new-dep philosophy across M3–M8.

---

### Decision 5: Pure `scrub(value)` function with pinned catalog

**Rationale:** PII scrubbing is security-critical; the pattern list is unit-tested with explicit pin tests. Adding a secret-shaped token requires updating both the catalog and the corpus, so the catalog can't grow silently.

**Trade-off:**
- Pro: clear audit trail, deliberate catalog maintenance
- Con: slightly more boilerplate than a generic regex library

**Precedent:** Aligns with security-first approach across M4 (input sanitization).

---

### Decision 6: Three-place correlation test (`test_end_to_end_trace`)

**Rationale:** The M11 gate requires end-to-end traceability. One test proves that the same `request_id` appears in all three artefacts (response header, access log, agent_logs row).

**Coverage:** If this test passes, the gate is met.

## Security review

### Threat model

| Threat | Mitigation | Status |
|---|---|---|
| Attacker pins logs to guessable `request_id` | UUID4 re-use only if hex-shaped; garbage replaced with fresh uuid | ✅ Secure |
| Attacker leaks secrets in query params / headers | `scrub()` walks all fields; bearer/JWT/email/card/SSN patterns redacted | ✅ Secure |

## Performance impact

### Latency overhead

- **Access-log middleware:** ~1ms per request (JSON serialization + logger write, non-blocking)
- **ContextVar ops:** <0.1ms (dict-like lookup)
- **Scrubber:** <1ms (regex on typically <1KB headers dict)

**Total:** ~2ms overhead per request (negligible for API endpoints already taking 50–200ms)

### Storage overhead

- **Access logs:** One JSON line per request (~300 bytes → ~30MB/day at 100 req/s)
- **agent_logs envelope:** `_request_id` adds ~40 bytes to `output` JSONB per log row (negligible vs. existing payload)

**Mitigation:** M11 does not add a new logging table; logs go to stdout (captured by infrastructure). `agent_logs` JSONB remains small.
