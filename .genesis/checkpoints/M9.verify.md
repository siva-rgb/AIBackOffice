### Quiz-me gate — Q+A block (logged per LOOPS.md §L4)

Quiz answer channel returned `I don't know / skip` ×3. Per strict protocol the
verdict would downgrade to UNCERTAIN at this point. **Owner direction
(`Accept verifier answers, finalise APPROVE`)** — owner accepted the verifier's
intended answers (below) as the Q+A block. Verdict finalised as APPROVE.

**Q1 (Design — registry-over-schema-derivation):**
*Question:* Why is a hand-maintained Python tuple in `app/backends/user_data.py::USER_DATA_TABLES`
preferable to deriving the table list from `information_schema` or extending
`seed_supabase.py::_CHILD_TABLES`?
*Verifier answer (accepted by owner):* A hand-maintained curated tuple is preferable because
(a) the mock backend has no `information_schema` to query — a Python constant is the lowest-
common-denominator both backends share; (b) the tuple is an allow-list of user-PII tables,
deliberately excluding audit/log tables that also carry `user_id` but aren't user-owned PII;
(c) the deletion FK children-before-parents ordering needs manual curation anyway
(information_schema would need topological sort at runtime) — a curated registry removes a
runtime failure mode and serves both backends.

**Q2 (Edge case — step 4 success + step 5 `admin.auth.admin.delete_user` failure):**
*Question:* If the `delete_user_data` DB wipe succeeds but the Supabase admin delete raises
(admin API down / network error / missing service-role env), what's the resulting state
and is it acceptable for a GDPR right-to-erasure?
*Verifier answer (accepted by owner):* The business PII is fully erased in every
`USER_DATA_TABLES` row + the `users` row; the Supabase auth identity lingers but can no
longer access data because the `users` row is gone and tokens are bound to it. The endpoint
returns `side_effects.auth_delete="skipped: <exc>"` so operator sees the failure; the audit
row captures what got cleared. **Acceptable for GDPR Art. 17** — erasure is best-effort
provided residual retention is logged and justified; support can re-issue the admin delete
once the Supabase admin API is back. No silent failure.

**Q3 (Change impact — pre-migration users):**
*Question:* `ALTER ... ADD COLUMN IF NOT EXISTS consent_version/consent_given_at` with no
DEFAULT — what happens to existing rows created before this migration, and does the M9.3
guard `if not updated.consent_version` handle them correctly?
*Verifier answer (accepted by owner):* Existing rows get NULL `consent_version`/
`consent_given_at`. The M9.3 onboarding-completion guard fires only when `onboarding_completed`
flips false→true — so **pre-migration already-onboarded users never auto-get consent
captured**. The only reconciliation path for them is `POST /api/account/consent`. By design,
this forces a one-time re-consent UX at M9 GA for the pre-existing user cohort — **but that
UX is not part of M9's scope**; recorded as a follow-up under §Follow-ups below.
