1. Background

Kora's agent_memory stores "remembered facts" about user businesses. Whenever the butler or supervisor needs context, memory_recall.recall() must find the most relevant past memories. Before M10, this worked by loading ALL rows for a user (100s-1000s) into Python and scoring each one via cosine similarity in a for-loop -- O(N) for every recall. The pgvector extension in Supabase stores vectors with an ANN (approximate nearest neighbor) index that reduces recall to O(log N).

The original migration file (2026-07-16) already had a comment anticipating this: "If a user's memory grows large, add ... an embedding vector(N) column, an ivfflat/hnsw index and a match_agent_memory RPC." M10 shipped that.

3. Code Walkthrough

The dual-column strategy

-- OLD column (keep forever -- backward compability)
embedding JSONB

-- NEW column (ANN-indexed, searchable across HNSW)
embedding_vec vector(1536)

Why both? The JSONB column is the canonical write target -- mock mode needs it, all existing reads work, zero migrations for existing consumers. The embedding_vec column is the ANN-indexed search surface. New inserts write both so they. old rows are back filled by a standalone script.

Migration: HNSW index + SECURITY DEFINER RPC

CREATE EXTENSION IF NOT EXISTS vector;
ALTER TABLE agent_memory ADD COLUMN IF NOT EXISTS embedding_vec vector(1536);
CREATE INDEX IF NOT EXISTS idx_agent_memory_embedding_vec_hnsw
    ON agent_memory USING hnsw (embedding_vec vector_cosine_ops);

CREATE FUNCTION match_agent_memory(
    p_user_id uuid,
    p_query_embedding vector(1536),
    p_match_threshold float DEFAULT 0.0,
    p_match_count int DEFAULT 10,
    p_filter_client uuid DEFAULT NULL,
    p_filter_kinds text[] DEFAULT NULL
)
RETURNS TABLE( ... ) LANGUAGE plpgsql SECURITY DEFINER AS $$
BEGIN
    IF auth.uid() IS NULL OR auth.uid() <> p_user_id THEN
        RETURN;  -- explicit tenant boundary, not just RLS
    END IF;
    RETURN QUERY
    SELECT ... FROM agent_memory ...
    ORDER BY embedding_vec <=> p_query_embedded
    LIMIT p_match_count;

HNSW vs IVFFLAT

HNSW was chosen because: - No training step needed (IVFFLAT requires a training scan) - Supports incremental INSERTs without rebuild - Same recall ceiling at per-user scale (100s-1000s rows) - vector_cosine_ops matches _cosine() in memory_recall.py that all Kora's scoring uses

The 3x k over-fetch

# recall() uses k * 3 over-fetch from ANN index
candidates = store.vector_search(user_id, q_vec, k * 3)
# Index ranks by cosine alone (ANN similarity)
# But hybrid scorer uses 4 weighted scores:
#  0.60 * semantic + 0.20 * lexical + 0.12 * displays + 0.08 * ground
# A wider candidate window lets the re-ranker correct
# index blind spots where recency/salience beats pure cosine

The backfill script

python -m scripts.backfill_agent_memory_vectors
# idempotent, page-based, hermatic-friendly (skips when no Supabase creds)
# Reads: WHERE embedding IS NOT NULL AND embedding_vec IS NULL
# Writes: embedding_vec = CAST(jsonb_to_vec(embedding) AS vector)ee
# Supports --dry-run, --reset, --batch flags

4. Key Design Decisions

HNSW over IVFFLAT

No training step, supports incremental inserts, same recall at per-user scale (100s-1000s rows). IVFFLAT needs list initialization via training rows — infeasible for small per-user partitions.

Dual-column JSONB + vector(N)

Don't drop the JSONB column — it's the canonical source-of-truth for mock mode, tests, and backfill. The vec column is the ANN search surface. Both written in parallel.

Default backend stays jsonb

AGENT_MEMORY_VECTOR_BACKEND=jsonb is the proven pre-M10 path. Operators flip to pgvector only after migration + backfill. No flag gated on real DB vs mock mode.

Same hybrid formula on both paths

Whether query gives to JSONB (O(N) Python) or pgvector (O(log N) ANN), the identical scoring formula is applied. Identical ranking for indexed vs non-indexed paths.

    Q1. Why is HNSW chosen over IVFFLAT for per-user memory?

    • HNSW requires large training sets that IVFFLAT can't handle
    • HNSW is easier to migrate from
    • HNSW has no training step, supports incremental INSERTs, and matches IVFFLAT on recall at per-user scale (~100s-1000s rows)
    • pgvector requires HNSW for cosine distance operations
    IVFFLAT, not HNSW, requires a training set (K-means clusters).
    C is correct. Per-user memory is 100s-1000s rows. HNSW is zero-config: no K-means training, no rebuild after INSERTs, equal quality at this scale.
    Migration is the same extension -- it's not about migration ease.
    pgvector supports both index types; HNSW is chosen because it fits the small per-user partition scale.

    Q2. Why keep BOTH JSONB and vector(N) columns rather than replacing JSONB?

    • vector(N) doesn't support INSERTs, so JSONB is needed for writes
    • JSONB is the canonical write target for mock mode and tests; vector(N) is ANN-indexed. Both write in parallel. No migration breakage
    • vector(N) column can't store JSON metadata, so a JSONB column is always required
    • Supabase doesn't support pgvector 2
    vector(N) does support INSERTs — otherwise the exp_backend wouldn't be inserting to it.
    B is correct. The JSONB column is the canonical source of truth for mock mode (no Postgres vector). The API doesn't change, tests don't break, backfill can snap from JSONB. The vec column is the search surface only.
    Agent memory uses separate columns for different purposes — no one column restriction.
    Supabase supports pgvector — the decision is not about support.

    Q3. Why 3x k over-fetch from the ANN index instead of fetching k directly?

    • To force a memory flush on the vector index
    • pgvector returns k+1 results by default
    • The index ranks by cosine similarity ALONE. Wider window lets hybrid re-ranker correct index mellitus spots using lexical+soundness+issue scores
    • To ensure SLAs for high-dimensional vectors
    No memory flush is triggered by a wider fetch.
    pgvector returns exactly what's requested.
    C is correct. ANN finds the 3*k most cosine-similar candidates. The hybrid re-ranker then applies lexical (seq), salience, and recency weights to the wider set. A user with 0.2 cosine similarity but 0.9 recency may beat one with 0.99 cosine but 0.0
    Wider fetch doesn't affect SLAs; it only makes the re-ranker more accurate.

    Q4. Should the operator see identical results from the JSONB path and the pgvector path?

    • Yes — both paths compute exactly the same answer
    • If on the same data fixture, yes — identical scoring formula applied on identical data gives identical ranking. But ANN search may miss a candidate. The _most questions_ influenced by ranking intractability
    • No — pgvector path always returns different order
    • Yes — both paths use the same underlying pgvector extension
    They give the same answer on TOPk when the user's data is identical (both use identical scoring). But the `sim` calculation differs slightly because pgvector uses the index-limited candidate set.
    B is closest. On the same data, the compute hybrid score is identical but the ILK candidates differ (ANN scan may miss a low-cosine but remaining question row that's not in the nearest_N). The MAX_k filter is typically enough to re-rank.
    They don't necessarily return different order, just a slightly different candidate set.
    The pgvector path uses map-match- with ANN, not exactly the same internal step.

    Q5. Why does the SECURITY DEFINER RPC include an explicit auth.uid() check inside its body rather than relying on RLS?

    • Supabase's RLS doesn't apply to RPC functions
    • The service role key bypasses RLS but doesn't bypass the RPC
    • SECURITY DEFINER without an explicit check would bypass RLS for the function's reads — exposing any tenant's memory
    • The enforce_plan route requires checks inside functions
    RLS does apply, but SECURITY DEFINER uses the owner's permissions — usually the service role — which bypasses RLS.
    The service role key also relates to the function context (the function runs with the creator's privileges, not the caller's)./
    C is correct. In Supabase, when a function is SECURITY DEFINER, it runs with the privileges of the user who created it (the function owner) — which is typically the database owner who bypasses RLS. Without the explicit check, the RPC would return results for any user.
    There's no enforcement attribute telling why.
