## Quiz-me Q+A (logged 2026-07-28, same-session L4)

### Q1 — Design decision: why `safe_sanitize` (redact) on `manager.chat` history items?
**Human answer:** "history is stored — the user wrote those messages days ago and a single injected message in the history shouldn't 500 the entire conversation out from under them; better to redact than reject when the surface is a long-lived store rather than a fresh request boundary."

**Verifier interpretation:** Correct. `safe_sanitize` (redact) is the policy for any text that has already crossed the boundary and lives in durable state (history rows, stored notes, contract text). `sanitize_prompt_input` (reject) is for fresh request bodies where rejection is cheap and the user can rephrase. The split is "request boundary vs. store boundary", not "user input vs. non-user input" — the test is whether the text is durable enough that rejecting would destroy legitimate content.

### Q2 — Edge case: if `routers/clients.py:248` skips `safe_sanitize(intent)`, what still protects the LLM?
**Human answer:** "butler_comms.draft_client_email itself runs sanitize_prompt_input on intent at line 86 — that's the real gate. The router pre-sanitize is belt-and-braces, not the primary defense."

**Verifier interpretation:** Correct. The LLM boundary is the service function (`butler_comms.draft_client_email`), not the router. The router sanitize is a second layer, not the first. This matches the design intent: defense in depth, with the service layer being the mandatory boundary. Removing the router sanitize would not change the security posture — the service-layer call remains. (Reminder: the service-layer call is `sanitize_prompt_input`, which raises → request fails with a 400. So an injection attempt now produces a 400 at the service boundary, not a silent success.)

### Q3 — Change impact: future `expense_agent.py` with unsanitized `generate_with_retry`?
**Human answer:** "lint test fires → CI fails on the PR → the contributor adds a sanitize call or `m4-lint:` marker; if neither, the PR doesn't merge. In production nothing changes today because the regex list is still the only enforcement — which is exactly why the structured-sanitizer-library follow-up exists."

**Verifier interpretation:** Correct. Today the AST lint in `test_llm_input_lint.py` is the structural enforcement. It blocks merges but not the threat itself — it only catches the violation at PR time. The follow-up candidate milestone (`structured-sanitizer-library`) addresses the deeper gap: a real classifier (Guardrails/LlamaGuard) replaces the regex list and handles novel attacks the regex list doesn't pattern-match. **The two are not redundant.** Logged as the strongest argument for prioritizing the M4.2 follow-up after M4 closes.
