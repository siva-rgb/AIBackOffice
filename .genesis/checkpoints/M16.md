## L1 BUILD — decisions
1. **All deploy logic in one script** `ops/deploy.sh` (invoked `bash ops/deploy.sh <mode>`, no exec
   bit needed → cross-platform). Four modes: `staging`, `prod-canary`, `prod-promote`,
   `prod-rollback`. Keeps the workflow YAML thin and lets the logic be syntax-checked + dry-run
   locally.
2. **`.github/workflows/deploy.yml`** — 4 jobs:
   - `verify` (push): hermetic backend pytest (mock mode, redis service) — the deploy gate.
   - `staging` (push, `environment: staging`): auto, 100% traffic, isolated `*-staging` services.
   - `production-canary` (push, `needs: staging`, `environment: production`): the reviewer gate —
     GitHub pauses the job until a `production`-Environment reviewer approves.
   - `production-traffic` (workflow_dispatch): manual `promote` / `rollback` / `canary`.
3. **Backend-first URL bake preserved** — `NEXT_PUBLIC_API_URL` is inlined at frontend build; the
   script deploys backend, reads its URL (canary → the tagged revision URL via `jq`), then builds
   the frontend against it. Same gotcha `cloudbuild.yaml`/`DEPLOY.md` already document.
4. **Canary via Cloud Run revision tags** (M16.4): `--no-traffic --tag=canary` → `update-traffic
   --to-tags canary=10` → `promote` = `--to-latest` (100%), `rollback` = `--to-tags canary=0`
   (stable never left, so rollback is instant + complete).
5. **Keyless auth** — Workload Identity Federation (`google-github-actions/auth@v2`), `id-token:
   write` per job. No SA key committed.
6. **Staging ≠ production isolation** — separate services (`*-staging` suffix), so a bad staging
   deploy cannot affect prod traffic.

**Files:** `ops/deploy.sh` (new), `.github/workflows/deploy.yml` (new), `DEPLOY.md` (+CI/CD section).
