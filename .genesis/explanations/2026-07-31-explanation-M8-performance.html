M8: Performance — First Pass

Performance Backend Async + Indexes Phase 1

Five performance bottlenecks fixed in one milestone. M8 targeted the most impactful wins: database indexes for dashboard queries, connection pooling, offloading PDF generation from route path, converting LLM calls to async, and background CSV import.

1. Background

Kora as MVP was functional but slow in core paths: dashboard loads did full table scans, every request created a new Supabase client, invoice PDF generation blocked the HTTP response, CSV uploads blocked for 50-row AI batches, LLM calls were synchronous, and the gather_state() helper was called 6 times per supervisor run without caching. M8 addresses each with minimal, targeted changes.

2. Intuition — The Five Bottlenecks

M8.1: Database Indexes — dashboard full scans become index scans

BEFORE (no Index)
SELECT * FROM invoices WHERE user_id = ?
ORDER BY created_at DESC LIMIT 50;
-- full table scan, ~500ms for 10K rows
AFTER (indexed)
CREATE INDEX idx_invoices_user_created
ON invoices(user_id, created_at DESC);
-- Index scan, ~5ms for any row count

M8.2: Connection Pooling — Per-request client creation to shared singleton

BEFORE
# Every request: create new client
_sb = create_client(url=..., key=...).
# 100 req/s = 100 client init, Handshakes,
# HTTPS handshakes per second
AFTER (pooled)
# app/clients/pool.py — singleton
_sb = get_supabase()  # once per process
# 100 req/s = 1 reused connection pool

M8.3: PDF Generation — Sync inline to BackgroundTasks

BEFORE
# routers/invoices.py (old)
def create_invoice(body):
    invoice = store.insert_invoice(...)
    pdf_path = generate_invoice_pdf(invoice)  # blocks
    store.update_invoice_pdf(...)
    return invoice  # 5-10s response
AFTER (BackgroundTasks)
def create_invoice(body, background_tasks):
    invoice = store.insert_invoice(...)
    background_tasks.add_task(generate_and_upload_pdf, invoice)
    return invoice  # ~50ms response

M8.4: Async LLM — Sync chat to achat/achat_messages

BEFORE (sync)
response = llm.chat(messages)
# blocks for 2-10s, blocks the FastAPI event loop
AFTER (async)
response = await llm.chat(messages)
# 2-10s call, FastAPI event loop continues
# processing other requests in parallel

M8.5: CSV Upload — foreground to background

BEFORE
POST /api/bookkeeping/ingest (CSV)
-> sync process CSV -> loop
   over 50 transactions with AI batches
-> block for 20-45s
-> return full parsed list
AFTER (job polling)
POST /api/bookkeeping/ingest

GET /api/bookkeeping/import/{job_id}

3. Code Walkthrough

Connection pool — clients/pool.py

import httpx
from supabase import create_client

_sb = None
_http = Non

def get_supabase():
    global _sb
    if _sb is None:
        _sb = create_client(url, key)
    return _sb

def get_http():
    global _http
    if _http is None:
        _http = httpx.AsyncClient(timeout=30)
    return _http

Two singletons: Supabase for DB queries, httpx for HTTP outbound (Stripe API, Google API). Created once at import, reused for all requests.

Per-request cache — request_cache.py

from contextvars import ContextVar

request_cache: ContextVar[dict] = ContextVar("request_cache", default={})

def cached_gather_state(user_id: str):
    cache = request_cache.get()
    if "gather_state" in cache:
        return cache["gather_state"]
    result = compute_gather_state(user_id)  # expensive
    cache["gather_state"] = result
    return result

ContextVar (not process-global) ensures no cross-tenant leakage. Within one request, the first gather_state call computes, subsequent calls return the cached value.

4. Key Design Decisions

ContextVar over process-global cache

The module-level dict would mix snapshots between users and requests. ContextVar scopes each request independently. Cost: 2 extra lines. Result: no cross-user leakage.

BackgroundTasks over Redis queue

FastAPI's BackgroundTask runs in the same process after the response. No Redis dependency, no broker monitoring, zero new infra. For a single-worker stage, this is enough. For multi-worker, migrate to Redis/Celery.

Module-level singleton client over dynamic creation

A singleton prevents TLS re-handshake overhead per request. The socket.get_supabase() guard ensures thread/process-safe singleton without actual formal locking.

Indexes driven by EXPLAIN ANALYZE

Only add indexes that actual query patterns benefit from. Don't pre-index on speculation. Every index slows down inserts, increases DB size.

    What distinguishes the Connection pool singleton from a per-request client?

    • It caches database credentials in-memory for faster lookup
    • It eliminates per-request TCP/SSL&A handshake overhead by reusing a warm pool
    • It is the only way to support concurrent Supabase queries
    Credentials are not cached — they're just passed to the create_client call
    The pool typically holds multiple connections to handle concurrent queries.
    C is correct. The singleton eliminates per-request TCP + SSL handshake (a cold 3-way TCP open + 2-trip SSL for each request). A warm pool reuses existing connection.
    Supabase client already supports concurrent queries — pool is about reuse, not concurrency.

    Q2. Why is ContextVar chosen for per-request cache over a global dict?

    • It's faster than a dict lookup
    • 's required by FastAPI's base middleware
    • A global dict would mix data between different users and requests
    • The project uses Django internally
    Dict isn't faster than ContextVar for this use case.
    It's not a FastAPI requirement — it's chosen for correctness.
    C is correct. A module-level dict maintains state from ALL requests globally across the process. ContextVar scopes each request independently. No cross-user leaks.
    Kora uses FastAPI, not Django.

    Q3. What happens if you call "send" immediately after a "create invoice" (before PDF generation finishes)?

    • The email sent will be missing the PDF attachment
    • The PDF will be corrupted because it was only partly generated
    • Backend ensures the PDF exists before emailing — generates it on demand if not ready
    • The endpoint returns HTTP 409 Conflict
    Backend won't email before PDF exists — it regenerates if needed.
    PDF generation is atomic — either the file exists or doesn't.
    C is correct. The backend's "send" method checks if the PDF exists; if it hasn't been generated yet by the background task, it regenerates synchronously before emailing.
    It doesn't fail — it regenerates the PDF on demand.

    Q4. Why are database indexes added only for ACTUAL query patterns (not guessed)?

    • All indexes are automatically created by Supabase
    • Adding an index has no performance cost
    • Every index costs INSERT/ (  pre slowdown) and extra disk space — must be cost-justified
    • Index management requires manual migration
    No. Indexes are explicitly created in migration files.
    Every index has write cost and disk cost.
    C is correct. An index is not free: every INSERT/UPDATE/DELETE on an indexed column triggers index-maintenance I/O. At Kora-scale, every wasted index compounds.
    Manual migration is unrelated to the decision not to create unnecessary indexes.
