**Q1 (Design — HNSW over IVFFLAT):**
*Question:* Per-user memory is 100s–1000s of rows; why choose HNSW over IVFFLAT
when IVFFLAT has smaller memory footprint at the documented scale?
*Verifier answer (accepted by owner):* HNSW is the right choice here for three
compounding reasons. (a) **No training step** — IVFFLAT requires `lists`-parameter
tuning against a representative sample, and a per-user memory table has skewed,
incremental growth that makes "the right `lists`" a moving target; HNSW builds
online. (b) **Incremental inserts without rebuild** — IVFFLAT's lists are static
at index-build time; new rows land in the nearest list's bucket but the index
quality degrades as the distribution drifts. HNSW's graph extends incrementally.
(c) **Same recall ceiling at this scale** — pgvector's own benchmark numbers and
Supabase's `vector-indexes` guide both show HNSW matching IVFFLAT's recall at
the 1k-100k row range, with HNSW winning on query latency. The only place
IVFFLAT wins is memory footprint, which is not a constraint here (per-user
memory is bounded by `len(memory_recall._DOCS)` * 1536 floats ≈ single-digit MB
per user). Operator tuning knob `SET hnsw.ef_search = N` is documented in the
migration comment at lines 34-36.

**Q2 (Edge case — `k*3` over-fetch + filter selectivity):**
*Question:* The pgvector branch over-fetches `k*3` candidates from the index, then
re-ranks with the hybrid formula. What happens when the optional `client_id` or
`kinds` filter is so selective that the post-filter result set falls below `k`?
*Verifier answer (accepted by owner):* The candidate window narrows, but two
mechanisms prevent under-returning. (1) The filters are pushed **inside** the RPC
(`migration:102-103`), not chained as PostgREST `.eq()` outer filters — so the
index planner can combine them with the vector predicate instead of discarding
rows after the similarity `LIMIT`. (2) `k*3` is a safe over-fetch at the
per-user scale: 3× the candidate window absorbs ~67% of the post-filter attrition
before under-returning. At extreme selectivity (e.g. one client_id among dozens),
pgvector ≥0.8.0's iterative index scans can re-enter the index for more
candidates (Supabase's `hnsw-indexes` doc); the operator can also raise
`AGENT_MEMORY_VECTOR_BACKEND`'s implicit window by raising `k` at the call site
— `memory_recall.recall()` already takes `k` as a parameter. The benchmark
fixture doesn't exercise this edge — recorded as a non-blocking FU-M10 filter-
selectivity test to add when the live Supabase benchmark runs.

**Q3 (Change impact — `ALTER TABLE agent_memory ADD COLUMN embedding_vec vector(1536)` on pre-migration rows):**
*Question:* What happens to existing `agent_memory` rows created before this
migration is applied? Do they get a default `embedding_vec`, and does the
pgvector branch break for them?
*Verifier answer (accepted by owner):* `ADD COLUMN IF NOT EXISTS embedding_vec
vector(1536)` adds the column with **no DEFAULT** — existing rows get
`embedding_vec = NULL`. The pgvector branch in `recall()` (`memory_recall.py:212`)
calls `vector_search_agent_memory()` which calls the RPC; the RPC's `WHERE`
contains `am.embedding_vec IS NOT NULL` (`migration:101`), so **NULL-vector rows
are silently excluded** from the candidate set. The JSONB `embedding` column is
still populated for these rows, so the JSONB branch (`memory_recall.py:222-225`)
still returns them. **Net effect:** until the operator runs
`scripts/backfill_agent_memory_vectors.py`, the pgvector path returns a
strict subset of the JSONB path's candidates (only rows with a populated
`embedding_vec`). This is **why the default stays `jsonb`** and the toggle is
operational — the operator must run the migration + backfill before flipping
`AGENT_MEMORY_VECTOR_BACKEND=pgvector`. The checkpoint correctly documents this
in M10.md §iter 1 §decisions §6 and in the backfill script's module docstring.
The order is enforced by documentation, not by a startup check — recorded as
FU-M10-startup-guard (non-blocking) since the failure mode is "returns fewer
candidates, never returns wrong rows" (the body-check still holds).
