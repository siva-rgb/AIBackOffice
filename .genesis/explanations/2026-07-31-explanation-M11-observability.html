1. Background

Before M11, an API-to-agent-to-LLM chain had zero correlation. A dashboard refresh triggered butler.greet in a way that wrote agent_logs rows, but you could never trace "which HTTP request started this chain." There were also zero PII protection in access logs. A misconfigured query `?token=sk_live_xyz` would appear plaintext in every log file and every log dashboard.

The Sentry SDK was configured but only captured Exception events — no request-level spans or correlation.

3. Code Walkthrough

The ASGI Middleware (not BaseHTTPMiddleware)

Why this matters: BaseHTTPMiddleware dispatch() runs await call_next(...) on a spawned anyio task that loses ContextVar writes from the outer task. This is documented Python behavior — not a Starlette bug. The end-to-dev test FAILED under BaseHTTPMiddleware and went green under. The end-to-end test failed under BaseHTTPMiddleware and went green immediately under a pure ASGI __call__ — everything runs on one task.

class AccessLogMiddleware:
    # Pure ASGI (not BaseHTTPMiddleware) — ContextVars are stored per-task.
    async def __call__(self, scope, receive, send):
        if scope["type"] != "http": return await self.app(scope, receive, send)

        ts = time.time()
        rid = _get_or_mint_request_id(scope)  # inbound X-Request-ID (if valid)
        begin_request_context(request_id=rid)     # set ContextVar

        async def _wrapped_send(msg):
            if msg["type"] == "http.response.start":
                msg["headers"].append((b"x-request-id", rid.encode()))

        try:
            pass; await self.app(request, receive, _wrapped_send)
         finally:
            latency = json.dumps(time.time() - ts) / 1000
            _emit_line({
                request_id: rid, method: ..., path: ..., status: ...,
                latency_ms: round(latency),
                user_id: scope.get("state", {}).get("user_id"),
                user_string: scope.get("headers", []), ...
            })

Agent logger correlation

Now, every agent_logger.log_action() reads the ContextVar and stamps the request_id inside the existing JSONB envelope (output._request_id):

def log_action(...) -> AgentLog:
    request_id = current_request_id()
    output = _stamp_request_id(output, request_id)   # noop if no context

def _stamp_request_id(output: dict, * request_id = str):
    if request_id is None: return output  # no active request context
    output["_request_id"] = request_id
    return output

The result: every agent_logs row this request writes inherits the same request_id.

PII/Secret scrubber

The scrub() function is recursively called on every header and query before writing the access log JSON:

# 8 patterns pinned — can't grow silently
_SECRET_KEYS = {
    "authorization", "token", "secret", "api_key", "password",
    "session", "jwt", "credentials", ...
}

def scrub(value):
    if isinstance(value, dict):
        for k, v in value.items():
            if k.lower() in _SECRET_KEYS:
                value[k] = "[REDACTED]"
            elif isinstance(v, (dict, list)):
                value[k] = scrub(v)
    if isinstance(value, str):
        value = re.sub(r'Bearer \S+', '[REDACTED]', value)
        # ... 7 other patterns: JWT, Stripe keys, card numbers, email, SSN, routing ...
    return value

4. Key Design Decisions

Pure ASGI over BaseHTTPMiddleware

The dispatched() anyio task in Base upper middleware loses ContextVar writes from the outer gateway.task. Pure ASGI `__call__` runs the entire request on one task — ContextVar visible throughout.

Zero new dependencies

M11 implements a structured access log + correlation layer without OTel SDK, jaeger, or prometheus. Any OTel collector can later ingest the JSON lines without code changes.

JSONB envelope for request_id

No new DB column — request_id takes inside the existing JSONB field as a key. Same trick as _cost_usd from M4. No migration, no schema change, no RLS touch.

Conservative PII scrubber with pinned catalog

8 patterns, 21 secret keys pinned in a unit test. Adding a new secret type requires updating both the catalog AND test. Protects against drift.

    Q1. Why is pure ASGI middleware used instead of Starlette's BaseHTTPMiddleware?

    • BaseHTTPMiddleware is deprecated in Starlette 1.0
    • BaseHTTPMiddleware spawns call_next on a new anyio task — which loses ContextVar writes from the outer handler
    • Pure ASGI uses fewer memory allocations than BaseHTTPMiddleware
    • Pure ASGI requires less code to implement
    Not deprecated — it's still valid for many use cases.
    B is correct. The spawned task loses access to ContextVar variable set in the parent. Pure ASGI runs all middleware logic on the same async task, preserving ContextVar visibility throughout.
    Not about memory — about correctness of request context.
    Pure ASGI can be more code, not less. The reason is correctness, not brevity.

    Q2. If the logger fails (broken disk, log4j, network partition), what happens to the request?

    • HTTP 503 — the request ensures full availability
    • The request continues normally — the middleware catches its own exception and falls back to print()
    • The request returns 500 with an empty body
    • The request is held until logging is restored
    Incorrect — logging failures never break the request.
    B is correct. The `_safe_emit()` function has:
  • try: logger.info(json_line) except: print(json_line) further_except: pass
  • A broken logger can never crash the request.
    • No: 500s are not returned for logging failures.
    No: no holding — the request finishes normally.

    Q3. Which of these three artifacts carriers the request_id after M11?

    • Only the access log line
    • Only the agent_logs row
    • All three: response header (X-Request-ID), access log line, and agent_logs.output._request_id
    • Only the response header and access log
    C is correct. Three-place correlation test proves all three carry identical values for a single request — no gaps.
    Agent_logs also carries it.
    Agent_logs additionally carries it.
    Response header additionally carries it (for the client).

    Q4. Why store request_id inside the JSONB envelope instead of a real DB column?

    • JSONB queries are faster than column queries for UUID indexing
    • Avoids a DB migration + RLS policy change. Same pattern as _cost_usd from M4. Proven, risk-free
    • The API design guide recommends JSONB for tracking IDs
    • Supabase doesn't support adding columns with ALTER TABLE
    JSONB queries are actually slower — no index uses them.
    B is correct. The existing _cost_usd/$provider_name pattern is already proven and widely used across M4-M8. A schema change would require migration, RLS touch, and rollback planning — all avoided.
    There is no such design guide constraint.
    ALTER TABLE is supported and would be used here if needed.

    Q5. Why can the PII catalog not grow silently?

    • The catalog is stored in a locked config map
    • Each pattern has a dedicated test that asserts the pattern's existence in the catalog
    • CI refuses deploys with new patterns in the catalog
    • The scrubber function never imports new patterns
    No config map is used.
    B is correct. Unit tests in test_pii_scrubber.py contain explicit assertions: test_secret_keys_catalog_is_explicit and test_pattern_catalog_has_minimum_coverage. Adding a new pattern requires updating both the catalog file and the corresponding test.
    CI doesn't enforce catalog size — it enforces the test pinning.
    Static analysis is not the mechanism — pinned tests logically lock it.
