## Plan

1. **Request context** — `backend/app/utils/request_context.py`: two `ContextVar`s (`current_request_id`, `current_user_id`) + a `begin_request_context(request_id)` / `end_request_context()` pair, mirroring `request_cache.py`. Sibling module so existing call sites don't import churn
2. **PII scrubber** — `backend/app/utils/pii_scrubber.py`: pure function `scrub(value, *, allow_keys: set[str] | None = None) -> Any`. Patterns: `Bearer <token>`, `Basic <token>`, JWT-shaped (`eyJ...`), `sk_live_*`/`sk_test_*`/`rk_live_*`, 16-digit card numbers, email addresses, paths containing `token`/`secret`/`api_key`/`password`. Allowlist for keys that should pass through (e.g. `request_id`, `user_id`, `created_at`)
3. **Access-log middleware** — `backend/app/middleware/access_log.py`: ordered **after** security-headers (so it sees the final status) and **before** Sentry's request middleware (when SDK is configured). Sets `request.state.request_id` (from inbound `X-Request-ID` if present and uuid-shaped, else `uuid4().hex`), calls `begin_request_context(request_id)` then `end_request_context()` on exit, emits one structured JSON line via the standard `logging` module under name `kora.access`. Add `X-Request-ID` to response headers. **Never raise** — a broken log must not break the request
4. **Sentry correlation** — extend `_scrub_sensitive_data` in `main.py` to also stamp `event.setdefault("tags", {})["request_id"] = current_request_id()` on every Sentry event so an unhandled exception carries the correlation id

- gate G5: deferred (L4 VERIFY next session — owner runs or asks the driver to)
- decisions:
  1. **Pure ASGI middleware (not `BaseHTTPMiddleware`).** `BaseHTTPMiddleware.dispatch()` runs `await call_next(...)` on a spawned anyio task and loses the outer task's `ContextVar` writes — a documented Python behaviour, not a workaround. The end-to-end test failed under `BaseHTTPMiddleware` (handler ran with no `request_id` visible) and went green immediately under a pure ASGI `__call__`. All on one task.
  2. **`request.state.user_id` mirror in addition to the ContextVar.** Same reason — `get_current_user` runs inside the spawned task (it doesn't matter for ASGI middleware, but the pattern is shared with future BaseHTTPMiddleware-style code paths), so the access-log middleware reads `request.state.user_id` to find what the auth dependency stamped.
  3. **`request_id` rides inside `agent_logs.output` JSONB envelope.** Same trick M4/M6 already use for `_cost_usd` / `_provider_name`. No new DB column → no migration, no RLS touch, no schema drift. The downstream consumer reads it via `log.output.get("_request_id")`.
  4. **Pure `scrub(value)` function with pinned catalog.** PII scrubbing is security-critical so the pattern list is unit-tested with explicit pin tests (`test_secret_keys_catalog_is_explicit`, `test_pattern_catalog_has_minimum_coverage`) — adding a secret-shaped token requires updating both the catalog and the corpus test, so the catalog can't grow silently.
  5. **Three-place correlation test (`test_end_to_end_trace.py`).** One request must show the same `request_id` in (a) the response header, (b) the access-log line, (c) the `agent_logs` row. This is the gate.
  6. **No OTel SDK / OTLP exporter.** Zero-new-dep principle (PLAN.md M11.2 says "OpenTelemetry distributed tracing"; we built a structured log + correlation-id layer that any OTel collector can later ingest without code changes). Real OTel/OTLP is a follow-up candidate (`observability-otel`).
  7. **No new `agent_logs` DB column.** Avoiding the migration + RLS touch was the deciding factor in choosing the JSONB envelope over a real column. If/when tenant-scoped log analytics need indexed `request_id` lookup, a column can be added then via the standard migration pattern.
- next: L4 VERIFY (separate model, fresh context) — owner to run or to ask the driver to do so. Until then, M11 stays `[~]`.
