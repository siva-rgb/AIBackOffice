Summary

M6 replaced the in-process rate limiter with a distributed Redis-backed sliding-window implementation and kept an in-memory fallback for local development. The old design used threading.Lock and a module-level _hits dict — fine for a single worker, but with 4 workers the effective limit quadrupled silently. Multi-instance deployments had no global enforcement at all.

Before — In-Process Sliding Window

The original backend/app/middleware/rate_limit.py used:

_hits: dict[str, list[float]] = {}
_lock = threading.Lock()

def check_rate_limit(user_id: str, limit: int = 10, window: int = 60) -> bool:
    now = time.time()
    with _lock:
        hits = _hits.get(user_id, [])
        hits = [t for t in hits if now - t < window]
        if len(hits) >= limit:
            return False
        hits.append(now)
        _hits[user_id] = hits
        return True

Problems at scale:

  • Per-worker counters: 4 Gunicorn/uvicorn workers each maintain their own _hits dict. A 10 req/min limit becomes 40 req/min effective (4 workers × 10).
  • Multi-instance: Two EC2 instances = 8 workers = 80 req/min per "10 req/min" policy. No global enforcement vector.
  • Process restart resets: Deploy or restart clears _hits. Burst allowance resets to full.

Intuition — Per-Worker vs Global Limits

Rate limiting is a distributed consensus problem in disguise: all workers must agree on a single count for each user. Using in-process dictionaries is like each waiter at a restaurant counting their own served tables and claiming "we're only at 5!" — when across all waiters the kitchen is handling 25 orders.

The core insight: a sliding window needs a shared, atomic counter. Redis provides three primitives that together form the solution:

  1. Sorted set (ZSET): timestamp as score; one entry per hit.
  2. ZREMRANGEBYSCORE: expire old hits in the same transaction.
  3. ZCARD: count remaining hits.

All three execute inside a Redis MULTI/EXEC pipeline — they are atomic regardless of concurrent workers.

Redis ZSET Pipeline (Core Algorithm)

async def check_rate_limit_redis(user_id: str, limit: int, window: int) -> bool:
    now = time.time()
    key  = f"ratelimit:{user_id}"
    cutoff = now - window

    pipe = redis.pipeline()
    pipe.zadd(key, {str(now): now})           # 1 — add current hit
    pipe.zremrangebyscore(key, 0, cutoff)     # 2 — remove expired
    pipe.zcard(key)                           # 3 — count remaining
    _, _, count = await pipe.execute()

    return count <= limit

Atomic pipeline: all three commands execute in one Redis transaction. No other writer can interleave between ZADD and ZCARD. The sliding window naturally expires old hits without an explicit cleanup loop.
