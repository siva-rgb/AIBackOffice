M1: Tenant Isolation Enforcement

Security Backend Next.js 14 + FastAPI + Supabase Critical

Kora is an AI-powered back-office SaaS. Before M1, tenant isolation was enforced manually — every developer writing a new store function had to remember to add .eq("user_id", user_id) to every query. One miss, and you get cross-tenant data leaks. M1 replaces that brittle pattern with a TenantQuery wrapper that makes the default path safe.

1. Background

Kora exposes per-user dashboards: invoices, contracts, transactions, engagements, proposals, and more. All of it lives in Supabase Postgres with Row-Level Security (RLS) disabled at the time (the service-role key bypasses RLS entirely). The backend connects via the Supabase Python client, _sb = get_supabase(), which uses the service-role key and has unfettered access to every row in every table.

The only line of defence before M1 was the .eq("user_id", user_id) clause appended to each query builder chain. With ~65 raw _sb.table(...) calls scattered across supabase_store.py, every new store function or refactor was a gamble. Murphy's law guarantees that eventually someone forgets the .eq() clause — and then one tenant sees another's data.

M1 introduced TenantQuery — a thin wrapper class that auto-injects the .eq("user_id", ...) filter on every read and write. The default path is now safe; bypassing it requires an explicit escape hatch (raw_table()) with a comment justifying why.

2. Intuition — Before & After

list_invoices — before M1

BEFORE (manual eq — brittle)
def list_invoices(user_id: str) -> list[Invoice]:
    r = (_sb.table("invoices")
         .select("*")
         .eq("user_id", user_id)  # ← don't forget this!
         .order("created_at", desc=True)
         .execute())
    return [Invoice(**row) for row in r.data]
AFTER M1 (wrapped — safe by default)
def list_invoices(user_id: str) -> list[Invoice]:
    r = (repo(user_id)
         .select("invoices")
         .order("created_at", desc=True)
         .execute())
    return [Invoice(**row) for row in r.data]

Notice: no more .eq("user_id", ...) at the call site. The repo(user_id) wrapper handles it. A developer writing a new store function can no longer forget the filter — it's impossible.

Insert — before M1

Before (no guard against mismatch)
def insert_invoice(row: dict) -> dict:
    # No validation — row["user_id"]
    # could be anyone's. Silently
    # inserts under whatever the
    # invoker passes.
    r = _sb.table("invoices").insert(row).execute()
    return r.data[0]
After M1 (validates at insert)
def insert_invoice(user_id: str, row: dict) -> dict:
    # _check_user_id raises ValueError
    # if row.user_id != caller's user_id
    r = repo(user_id).insert("invoices", row).execute()
    return r.data[0]

The before path is silently dangerous — nothing stops a bug in caller composition from mixing data across tenants. The after path with _check_user_id catches the mismatch instantly.

3. Code Walkthrough

The TenantQuery class

Located in backend/app/backends/repository.py (68 lines). Constructed with (client, user_id), holds a fluent method set for every CRUD operation.

Reads

def select(self, table: str, columns: str = "*"):
    return self._client.table(table).select(columns).eq("user_id", self._user_id)

select automatically appends .eq("user_id", ...). The caller chains further modifiers like .order(), .limit(), .execute() as needed.

Writes — Insert with validation

def insert(self, table: str, row: dict):
    self._check_user_id(row)
    return self._client.table(table).insert(row)

The critical guard is _check_user_id. It verifies that the row being inserted either has no user_id key or has a value matching the wrapper's tenant. If there's a mismatch, it raises ValueError immediately with a descriptive message. After that, it stamps row["user_id"] = self._user_id so the caller doesn't have to pass it explicitly either.

Update & Delete

def update(self, table: str, patch: dict, record_id: str, id_col: str = "id"):
    return self._client.table(table).update(patch).eq(id_col, record_id).eq("user_id", self._user_id)

def delete(self, table: str, record_id: str, id_col: str = "id"):
    return self._client.table(table).delete().eq(id_col, record_id).eq("user_id", self._user_id)

Both enforce scoping: the update/delete only applies if the record's user_id matches the tenant AND the primary key matches. This prevents deleting/updating another tenant's row.

Upsert

def upsert(self, table: str, row: dict, on_conflict: str):
    self._check_user_id(row)
    return self._client.table(table).upsert(row, on_conflict=on_conflict)

Upsert also passes through _check_user_id, so even conflict resolution can't slip in wrong-tenant data.

The escape hatch — raw_table

def raw_table(self, table: str):
    """Direct table access — only for queries that cannot use user_id
    (e.g. cross-tenant admin ops using the service-role key).
    Every call site must carry a comment explaining why this is safe."""
    return self._client.table(table)

raw_table() returns the bare Supabase table scope without injecting .eq("user_id", ...). This is necessary for operations that are genuinely tenant-agnostic (admin dashboards, system tables, auth queries). The difference? Using raw_table() requires explicit intent and a comment in code — it can't happen by accident. After M1, only 9 remaining raw_table accesses remain in the entire codebase, each with a comment justifying them.

The repo factory

def repo(client: Client, user_id: str) -> TenantQuery:
    return TenantQuery(client, user_id)

A simple factory. In supabase_store.py, it's wrapped as a module-level helper so every store function calls repo(user_id).

4. Key Design Decisions

Wrapper over ORM

No new ORM or database abstraction was added. TenantQuery wraps the existing Supabase query builder and adds the single missing behavior: tenant scoping. Minimal surface, maximum impact.

Insert-time validation

_check_user_id validates at insertion that the row's user_id matches the tenant's. Mismatch raises ValueError. This catches API-level composition bugs before they corrupt data.

Escape hatch by design

raw_table() exists because not every query fits a user_id filter (admin lookup, auth, memory). But the method name is conspicuously verbose — it signals "I know what I'm doing." Every call site requires a comment.

RLS is defense-in-depth

Supabase RLS policies were added via migration as a backup layer. If a raw escape-hatch call ever leaks, or the service-role key is misused, the database itself refuses cross-tenant rows. The application layer remains the primary guard.
